# DSH 多开

CodexSwitch 的内置插件 **DSH 多开** 让你同时运行多个 DSH 实例：每个实例是一个
独立的常驻进程，各自绑定一个端口，互不干扰。

- 插件标识：`dsh-multi`
- 位置：`src/codex_switch/builtin_plugins/dsh-multi/`
- 权限：`exec`（启动进程）、`fs:read` / `fs:write`（根目录 `~/.dsh`）、
  `snapshot:read`、`action:invoke`

---

## 1. 为什么需要它

DSH 默认一个 harness home（`~/.dsh`）只服务一个前台实例：会话、设置、登录态
都在这一份数据上。想"一边跑长任务、一边开另一个窗口干别的"时，单实例就不够用
了。

本插件把"再开一个 DSH"变成一次点击：它负责启动进程、等待就绪、解析访问地址、
停止进程、保留日志。

## 2. 两种隔离模式

| 模式 | harness home | 登录态 / 设置 / 会话 | 适用场景 |
| --- | --- | --- | --- |
| **共用**（默认） | `~/.dsh` | 与主实例共用，无需重新登录 | 同一账号开多个并行窗口 |
| **独立** | `~/.dsh/codex-switch-instances/homes/<实例名>` | 完全隔离，首次需重新登录与配置 | 多账号、多身份、互不污染 |

独立模式通过给子进程注入 `DSH_HOME` 实现。这个环境变量是 DSH 官方支持的
harness home 覆盖方式（优先级高于默认的 `~/.dsh`）。

> 独立 home 首次启动会自行初始化 profile。实测这一步并不复制整套依赖：
> `profiles/node_modules` 是指向安装位置的**链接**，冷启动通常在 10 秒内完成。

## 3. 界面怎么用

进入「插件中心」→ 选中「DSH 多开」。

1. **新建实例**：填实例名（必填），选类型（当前支持 Web 界面），端口填 `0`
   表示由系统自动分配（推荐，绝不会撞端口）。需要独立身份时打开「独立 home」。
2. **启动**：点「启动」后插件会**等到实例真的就绪**才返回——判定依据是日志里
   出现了带 token 的访问地址。因此看到「运行中」就一定能打开。
3. **打开**：点「打开」会用系统默认浏览器打开该实例的地址（地址也在列表里）。
4. **日志**：点「日志」查看该实例的输出，启动失败时这里能看到真实原因。
5. **停止 / 全部停止**：结束单个实例或全部实例。
6. **删除**：移除实例记录（运行中的会先停止）。**独立 home 目录不会被删除**，
   以免误删数据。

## 4. 关键设计取舍

### 为什么不用宿主的 `api.run_command` 启动

宿主提供的 `run_command` 是 `subprocess.run(..., timeout=120)`，而 DSH 实例是
**永不退出的常驻进程**。用它启动会阻塞满 120 秒再抛超时，期间界面还会卡住。
所以插件自己用 `subprocess.Popen` 启动，并把 stdout/stderr 重定向到日志文件。

### 为什么"进程活着"不算启动成功

端口被占用时，DSH 会报错重试而不会立刻退出。仅凭"进程还在跑"就报成功，用户
会拿到一个打不开的地址。因此 web 实例的判据是日志里出现
`dsh web: http://...` 这一行；启动失败时插件会终止子进程（避免留下占着端口的
孤儿），并把日志里的错误摘出来作为提示。

### 每次启动都会清空日志

否则上一轮留下的 URL 行会让"本次是否就绪"永远为真。

### 关掉 CodexSwitch 不会杀掉实例

多开的意义就是让它们独立存活。卸载插件时**只**记录一条日志，运行中的实例继续
跑；需要停止时请用界面上的「停止」。

### 关掉 CodexSwitch 后重新打开

本会话启动的实例状态记录在内存里。程序重启后，插件不再持有进程句柄，因此会把
它们显示为「已停止」——即使进程其实还在跑。这是刻意的保守选择：宁可让你手动
确认一次，也不要把一份过期的日志误报成"正在运行"。你可以在系统里结束残留进程，
或者重新启动一个新的实例。

## 5. 数据与路径

| 内容 | 路径 |
| --- | --- |
| 实例注册表 | `~/.dsh/codex-switch-instances/instances.json` |
| 实例日志 | `~/.dsh/codex-switch-instances/logs/<实例名>.log` |
| 独立 home | `~/.dsh/codex-switch-instances/homes/<实例名>` |

它们整体跟随 harness home；`DSH_HOME` 一变，这些路径也跟着变。

## 6. 环境变量

| 变量 | 作用 |
| --- | --- |
| `DSH_BIN` | 显式指定 dsh 入口（PATH 里没有 dsh 时用）。可写 `dsh`、`.cmd` 路径，或 `node <bin.js>` 形式 |
| `DSH_NODE_BIN` | 指定 node 可执行文件（默认从 PATH 查找） |
| `DSH_INSTANCES_DIR` | 覆盖多开数据目录（便于测试与隔离） |
| `DSH_HOME` | DSH 自身的 harness home 覆盖；独立模式的实例会被注入这个变量 |

插件定位 `dsh` 的顺序：`DSH_BIN` → `PATH` 上的 `dsh` → npm 的 `_npx` 缓存。
找不到时会给出可操作的提示，而不是静默失败。

## 7. 常见问题

**点「启动」后提示超时？**
看「日志」。最常见的是端口被占用（`EADDRINUSE`）或首启动初始化较慢。把端口改
成 `0` 让系统分配可以排除端口冲突。

**找不到 dsh 命令？**
说明 DSH 不在 PATH 上。设置 `DSH_BIN` 指向入口即可，例如
`C:\Users\你\AppData\Local\npm-cache\_npx\<hash>\node_modules\.bin\dsh.cmd`。

**独立模式的实例要我重新登录？**
这是预期行为：独立 home 是一份全新的 harness home，凭据不复用。这正是"隔离"
的含义。若不想重新登录，请使用默认的共用模式。

**打开了地址但页面 401？**
该地址需要先完成一次 token 交换并写入 cookie（浏览器会自动做）。插件给出的
完整地址带 `?token=...`，直接用浏览器打开即可；不要只复制域名部分。

## 8. 实现位置

| 文件 | 职责 |
| --- | --- |
| `builtin_plugins/dsh-multi/plugin.json` | 清单：权限、动作、入口与页面 |
| `builtin_plugins/dsh-multi/entry.py` | 插件层：把界面调用翻译成核心动作，返回结构化结果 |
| `builtin_plugins/dsh-multi/page.qml` | 插件页面：实例列表、新建表单、详情与日志 |
| `codex_switch/dsh_instances.py` | 核心逻辑：注册表、启动计划、URL 解析、进程状态机 |
| `codex_switch/dsh_home.py` | harness home 解析（DSH 多开与 CodeBuddy 快照共用） |
| `codex_switch/process_util.py` | 进程/日志工具（与 AI 终端的脚本运行器共用） |
| `tests/test_dsh_multi.py` | 单元测试 + QML 渲染测试 |

核心逻辑刻意不依赖 Qt，因此可以在没有 Qt 的环境里直接单测。
